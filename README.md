# 可能性星云 · chess-cloud

下一步棋之后的所有可能未来，一次全画出来。

点开就能玩：你执白落一子，当前局面变成星云的核心，之后每一层合法走法向外炸开成星。
星的颜色是那个未来的评估分：**暖色=白方占优，冷色=黑方占优，中性灰=均势**。
黑方由一个自写的 minimax + alpha-beta 引擎在 Web Worker 里应手。

**在线玩**：https://maxi-max-dev.github.io/chess-cloud/

## 星云里到底有多少颗星

以起始局面为例，四层全展开：

| 层 | 含义 | 星数 |
|---|---|---|
| 0 | 当前局面自己 | 1 |
| 1 | 白方所有走法 | 20 |
| 2 | 再加黑方所有应手 | 400 |
| 3 | 第三步 | 8,902 |
| 4 | 第四步 | 197,281 |

这些不是估算，也不是写死在页面里的数字：页面把每一层的星数从 three.js 几何体的
`position.count` 现读出来，`verify.mjs` 在 Node 里独立递归数一遍全树，两边必须一个不差。
第 4 层的 197,281 颗是公认的 perft(4) 标准值。

## 怎么跑起来的

- 前 3 层（9,322 颗）主线程同步铺开，约 150–200ms，落子后立刻成形。
- 第 4 层（起始局面 197,281 颗）交给 Web Worker，按父节点分批算、分批送回主线程，
  边算边长。同步算这一层要 8 秒，会把页面卡死，所以它必须在 Worker 里。
- AI 用迭代加深搜索，思考预算 1.5 秒，时间到就交上一层搜完的最好走法，
  所以应手时间有硬上限（实测起始局面 e4 后约 2.3 秒完成应手，搜到 4 层）。
- 评估函数（子力 + 位置表）全项目只有一份，在 `engine.js` 里。
  星的颜色和 AI 眼里的好坏读的是同一个函数——不然画面和棋力就是两个世界。

## 脉络（树视图）

右边那半屏是一棵从下往上长的树，回答的是「这一步之后到底发生了什么」：

- **下半截是走过的路**：每一层摊开当时所有的合法走法，实际走的那条金色高亮。
  一眼看到「他当时有 20 条岔路，选了 Nc6」。
- **中间一条虚线是「现在」**，往上都还没发生。
- **上半截是还没走的岔路**：默认那条蓝线是「每步只按眼前这一步谁占便宜」挑出来的，
  不是最优解。点任意一个点，树就顺那条重新往上长。
- 鼠标停在任何一个点上，左边棋盘会把那一步画出来，底下告诉你这步之后对方有多少种回应。

树上每一层的岔路数也是防作弊的：页面把 `<circle>` 从 SVG 里真数出来，
`live-check.mjs` 拿 `count(该层局面, 1)` 去撞，走过的那条线还要和真实棋谱逐字对上。

## 文件

- `index.html` — 页面：自绘 SVG 棋盘、three.js 星云、视角控制
- `engine.js` — 唯一的评估函数 + minimax 搜索 + 逐层展开
- `worker.js` — Web Worker：AI 应手 / 第 4 层星云，页面各开一个实例
- `verify.mjs` — Node 端验收：递归数全树，和 perft 标准值对撞

不用打包、不用构建、没有后端。chess.js 和 three.js 直接从 CDN 引。

```bash
node verify.mjs                                      # 棋核验收（需先 npm i chess.js@1.4.0）
node live-check.mjs                                   # 无头 Chrome 真机验收（本地起服务器）
node live-check.mjs --url https://maxi-max-dev.github.io/chess-cloud/   # 打线上
```

## 已知边界

- 兵到底线默认升变成后，没做选棋子的界面。
- 搜索只判将死和困毙，不判三次重复 / 50 步 / 子力不足和棋，残局会略微自我感觉良好。
- 星云的第 4 层直接对子局面做静态评估，「子局面正好是困毙」这种极少数情况会被当成普通局面上色。
- 面板宽度是固定像素，手机竖屏没适配。
- 点星预览某个未来、穿越进去继续下——下一期。
